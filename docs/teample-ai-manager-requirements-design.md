## 0. 프로젝트 개요

### 0.1 프로젝트 정의

**프로젝트명:** Teample AI Manager(팀플 AI 매니저)

**목표:** 대학 팀 프로젝트의 카카오톡 대화 내용을 사용자가 붙여넣으면 AI가 논의 내용, 결정 사항, 미결정 사항, 담당자별 할 일과 다음 안건을 구조화된 회의록으로 생성하고, 사용자가 이를 직접 검토·수정·확정할 수 있는 안전한 웹 서비스를 개발한다.

**핵심 가치:**

- 흩어진 메신저 대화를 사람이 다시 정리하는 시간을 줄인다.
- AI 결과를 자동 확정하지 않고 사람이 최종 검토하는 Human-in-the-loop 원칙을 적용한다.
- 프로젝트별 회의록을 일관된 구조로 축적해 결정과 할 일을 추적할 수 있게 한다.
- 대화 원문과 AI API 키 등 민감정보를 안전하게 처리한다.

### 0.2 개발 범위

이번 설계의 1차 MVP 범위는 다음과 같다.

1. 이메일 기반 회원가입·로그인
2. 프로젝트 생성·조회·삭제 및 팀원 이름 관리
3. 카카오톡 대화 원문 입력
4. Claude API를 이용한 구조화 회의록 생성
5. 프로젝트별 회의록 목록·상세 조회
6. AI 생성 결과의 사용자 수정·확정
7. 회의록 삭제
8. 사용자별 접근 제어, 입력 검증, AI 남용 방지 및 개인정보 보호

실시간 협업 편집, 메신저 자동 수집, 캘린더 연동, 파일 첨부, 조직 단위 관리자 기능은 1차 MVP 범위에서 제외한다.

### 0.3 기술 스택 및 배포 목표

| 구분 | 기술 | 역할 |
|---|---|---|
| 프론트엔드 | Next.js App Router, React, TypeScript, Tailwind CSS | 화면, 입력 검증, API 호출 |
| 인증 | Supabase Auth | 사용자 가입·로그인, JWT 발급 |
| 백엔드 | Spring Boot, Java 17, Spring MVC, Bean Validation | REST API, 권한 검증, 비즈니스 로직 |
| 데이터 접근 | Spring Data JPA, Hibernate | 영속성 및 트랜잭션 |
| 데이터베이스 | Supabase PostgreSQL | 프로젝트·회의록 저장 |
| AI | Anthropic Java SDK, Claude | 대화 분석 및 회의록 JSON 생성 |
| API 명세 | springdoc-openapi | 백엔드 계약 및 프론트 타입 생성 |

현재 저장소의 잠금 버전은 프론트엔드 Next.js 16.2.10, 백엔드 기능 브랜치 Spring Boot 4.0.2이다. 프로젝트 규칙 문서의 Next.js 15·Spring Boot 3 표기와 차이가 있으므로 구현 전에 기준 버전을 하나로 확정해야 한다.

## 1. 요구사항 도출

### 1.1 이해관계자와 사용자 역할

| 역할 | 설명 | 주요 권한 |
|---|---|---|
| 비회원 | 인증되지 않은 방문자 | 랜딩, 로그인, 회원가입 |
| 일반 사용자 | 인증된 서비스 사용자 | 본인 프로젝트와 회의록 생성·조회·수정·삭제 |
| 프로젝트 소유자 | 프로젝트를 생성한 사용자 | 프로젝트 정보·팀원 관리, 프로젝트 삭제 |
| 외부 AI 제공자 | Claude API | 전달된 대화를 구조화된 결과로 반환 |
| 운영자 | 배포·장애·보안 담당자 | 비밀정보·로그·모니터링 관리, 사용자 콘텐츠 임의 열람 금지 |

MVP에서는 프로젝트 구성원을 실제 계정과 연결하지 않고 AI 분석에 사용할 이름 목록으로 관리한다. 따라서 데이터 접근 권한은 프로젝트 소유자에게만 부여한다. 향후 공동 편집을 도입할 때 `project_members` 권한 모델로 확장한다.

### 1.2 핵심 사용자 시나리오

1. 사용자는 회원가입 후 로그인한다.
2. 과목명 또는 팀 프로젝트명을 입력하고 팀원 이름을 등록한다.
3. 프로젝트에서 새 회의록을 선택하고 회의 날짜, 선택적 제목, 카카오톡 대화를 입력한다.
4. 서버는 사용자·프로젝트 권한과 입력값을 검증한 후 Claude API에 구조화 요청을 보낸다.
5. 서버는 AI 응답을 JSON 스키마로 검증하고 임시 회의록으로 저장한다.
6. 사용자는 제목, 논의, 결정, 미결정 사항, 할 일, 다음 안건을 검토하고 수정한다.
7. 사용자는 결과를 저장·확정하거나 필요하면 삭제한다.

### 1.3 기능 요구사항 요약

| 번호 | 요구사항 | 우선순위 | 설명 |
|---|---|---:|---|
| FR-1 | 회원 인증 | 필수 | 사용자는 안전하게 가입·로그인·로그아웃할 수 있어야 한다. |
| FR-2 | 프로젝트 관리 | 필수 | 본인 프로젝트를 생성·조회·수정·삭제할 수 있어야 한다. |
| FR-3 | 팀원 이름 관리 | 필수 | AI 담당자 매칭에 사용할 팀원 이름을 관리할 수 있어야 한다. |
| FR-4 | AI 회의록 생성 | 필수 | 대화 원문을 구조화된 회의록으로 변환할 수 있어야 한다. |
| FR-5 | 회의록 조회 | 필수 | 프로젝트별 목록과 개별 상세 내용을 조회할 수 있어야 한다. |
| FR-6 | 회의록 편집·확정 | 필수 | AI 결과를 사람이 수정하고 확정할 수 있어야 한다. |
| FR-7 | 회의록·프로젝트 삭제 | 필수 | 소유자가 데이터를 삭제할 수 있어야 한다. |
| FR-8 | 오류·처리 상태 안내 | 필수 | 생성 중, 실패, 재시도 가능 여부를 명확히 표시해야 한다. |
| FR-9 | 감사·생성 메타데이터 | 권장 | 생성 시각, 수정 시각, 모델과 처리 상태를 기록해야 한다. |

### 1.4 FR-1 회원 인증 - 세부 요구사항

- 비회원에게 로그인·회원가입 화면을 제공해야 한다.
- 이메일은 정규화 후 유일해야 하며, 비밀번호 정책을 서버 또는 인증 제공자가 검증해야 한다.
- 비밀번호 원문은 애플리케이션 DB와 로그에 저장하지 않아야 한다.
- 로그인 성공 후 발급된 토큰은 백엔드가 서명, 발급자, 대상, 만료 시각까지 검증해야 한다.
- 로그아웃 시 클라이언트 세션을 제거하고 만료된 토큰의 재사용을 허용하지 않아야 한다.
- 인증되지 않은 사용자가 보호 API를 호출하면 `401 Unauthorized`를 반환해야 한다.

**인수 조건:** 서로 다른 두 계정으로 로그인했을 때 각 계정은 상대방의 프로젝트 목록과 회의록에 접근할 수 없어야 한다.

### 1.5 FR-2 프로젝트 관리 - 세부 요구사항

- 인증된 사용자는 프로젝트명과 팀원 이름 목록으로 프로젝트를 생성할 수 있어야 한다.
- 프로젝트명은 공백 제거 후 1~100자여야 한다.
- 사용자는 본인이 소유한 프로젝트 목록만 최신순으로 조회할 수 있어야 한다.
- 프로젝트 상세 화면은 프로젝트명, 팀원, 회의록 목록을 표시해야 한다.
- 프로젝트명과 팀원 목록을 수정할 수 있어야 한다.
- 프로젝트 삭제 전 사용자 확인 절차가 있어야 한다.
- 존재하지 않는 프로젝트는 `404`, 권한이 없는 프로젝트는 정보 노출을 줄이기 위해 동일하게 `404`로 응답할 수 있다.

### 1.6 FR-3 팀원 이름 관리 - 세부 요구사항

- 팀원 이름은 프로젝트당 1명 이상 30명 이하로 제한한다.
- 각 이름은 공백 제거 후 1~30자여야 한다.
- 동일 프로젝트 안의 완전히 같은 이름은 중복 저장하지 않는다.
- 팀원 이름은 Claude가 대화 속 담당자를 매칭할 때 참고정보로만 사용한다.
- AI가 목록에 없는 담당자를 생성한 경우 결과를 거부하거나 `미정`으로 정규화하고 사용자가 수정할 수 있게 한다.

### 1.7 FR-4 AI 회의록 생성 - 세부 요구사항

- 사용자는 회의 날짜, 카카오톡 대화 원문, 선택적 제목을 입력할 수 있어야 한다.
- 날짜는 유효한 ISO 날짜여야 하고 대화 원문은 1~20,000자로 제한한다.
- 제출 전에 현재 사용자가 해당 프로젝트 소유자인지 서버에서 확인해야 한다.
- 서버는 프로젝트명과 팀원 목록을 함께 사용해 Claude에 분석을 요청해야 한다.
- AI 결과는 다음 구조를 가져야 한다.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---:|---|
| `title` | string | O | 간결한 회의록 제목 |
| `topic` | string | O | 회의 주제 한 줄 요약 |
| `discussions` | string[] | O | 주요 논의 내용 |
| `decisions` | string[] | O | 최종 결정 사항 |
| `pending` | string[] | O | 미결정 사항 |
| `todos` | object[] | O | 담당자, 업무, 마감일 |
| `nextAgenda` | string[] | O | 다음 회의 안건 |

- 사용자가 제목을 직접 입력한 경우 이를 우선하고, 비워둔 경우 AI 제목을 사용한다.
- AI는 대화에 없는 사실을 임의로 추가하지 않도록 지시해야 한다.
- AI 응답이 비어 있거나 JSON 스키마를 만족하지 않으면 저장하지 않고 안전한 오류를 반환해야 한다.
- 같은 요청의 중복 제출로 회의록이 여러 개 생성되지 않도록 멱등키를 지원해야 한다.

**인수 조건:** 정상 대화를 제출하면 모든 필드가 존재하는 초안 회의록이 한 건 생성되고, 비정상 AI 응답이면 불완전 데이터가 DB에 남지 않아야 한다.

### 1.8 FR-5 회의록 조회 - 세부 요구사항

- 프로젝트 상세 화면은 회의록 제목, 회의 날짜, 생성 시각을 최신순으로 표시해야 한다.
- 회의록 상세 화면은 구조화된 모든 항목을 읽기 쉬운 구역으로 표시해야 한다.
- URL의 `projectId`와 `minutesId`가 실제 부모-자식 관계인지 서버에서 검증해야 한다.
- 프로젝트 소유자가 아닌 사용자는 URL을 추측해도 회의록을 조회할 수 없어야 한다.
- 빈 목록과 로딩·오류 상태를 구분해 표시해야 한다.

### 1.9 FR-6 회의록 편집·확정 - 세부 요구사항

- 사용자는 제목과 주제를 수정할 수 있어야 한다.
- 논의, 결정, 미결정, 다음 안건 항목을 추가·수정·삭제할 수 있어야 한다.
- 할 일의 담당자, 업무 내용, 마감일을 추가·수정·삭제할 수 있어야 한다.
- 저장 시 모든 필드에 서버측 길이·개수 검증을 적용해야 한다.
- AI 생성 직후 상태는 `DRAFT`, 사용자가 검토를 마치면 `CONFIRMED`로 전환할 수 있어야 한다.
- 동시 수정 덮어쓰기를 막기 위해 버전 또는 수정 시각 기반 낙관적 잠금을 적용해야 한다.

### 1.10 FR-7 회의록·프로젝트 삭제 - 세부 요구사항

- 회의록 삭제는 해당 프로젝트 소유자만 수행할 수 있어야 한다.
- 프로젝트 삭제 시 하위 회의록도 하나의 트랜잭션 안에서 삭제되어야 한다.
- 삭제 버튼은 확인 절차를 제공하고 성공 후 상위 목록으로 이동해야 한다.
- 삭제 요청은 다른 프로젝트의 자원을 지정하는 방식으로 우회할 수 없어야 한다.
- 개인정보 최소화 정책에 따라 삭제된 대화 원문이 애플리케이션 로그나 AI 응답 로그에 남지 않아야 한다.

### 1.11 FR-8 오류·처리 상태 안내 - 세부 요구사항

- AI 처리 중 중복 제출을 막고 진행 상태를 표시해야 한다.
- 네트워크 오류, 입력 오류, 인증 만료, AI 제공자 오류를 구분 가능한 메시지로 표시해야 한다.
- 사용자에게 스택 트레이스, SQL, 내부 호스트명, API 키 등 내부 정보를 노출하지 않아야 한다.
- 재시도 가능한 오류는 재시도 방법을 제공하되 자동 무한 재시도는 금지한다.
- 요청마다 추적용 `requestId`를 반환해 운영 로그와 연결할 수 있어야 한다.

### 1.12 비기능 요구사항

| 번호 | 영역 | 요구사항 및 측정 기준 |
|---|---|---|
| NFR-1 | 보안 | OWASP Top 10의 주요 위험을 방어하고 모든 보호 API에 인증·객체 단위 권한 검사를 적용한다. |
| NFR-2 | 개인정보 | 대화 원문을 최소 수집하고 로그에서 마스킹하며 삭제 요청 시 연관 데이터를 제거한다. |
| NFR-3 | 성능 | 일반 CRUD API의 서버 처리시간 p95를 500ms 이내로 목표로 한다(AI 처리시간 제외). |
| NFR-4 | AI 응답성 | AI 생성 요청은 60초 타임아웃을 적용하고 진행 상태를 표시한다. |
| NFR-5 | 가용성 | AI 제공자 장애가 프로젝트·기존 회의록 조회 기능까지 중단시키지 않아야 한다. |
| NFR-6 | 사용성 | 주요 작업은 명확한 로딩, 빈 상태, 성공, 실패 피드백을 제공한다. |
| NFR-7 | 접근성 | 키보드만으로 폼을 사용할 수 있고, 레이블·포커스·명도 대비를 제공한다. |
| NFR-8 | 호환성 | 최신 Chrome, Safari, Edge의 최근 두 개 주 버전을 지원한다. |
| NFR-9 | 유지보수성 | Controller-Service-Repository 계층과 DTO를 분리하고 OpenAPI 계약을 단일 기준으로 사용한다. |
| NFR-10 | 관측성 | 구조화 로그, requestId, 오류율, AI 지연·실패율을 수집하되 원문·토큰·비밀정보는 기록하지 않는다. |
| NFR-11 | 비용 통제 | 사용자별 AI 요청 속도·일일 횟수·입력 크기를 제한한다. |
| NFR-12 | 데이터 무결성 | 프로젝트와 회의록 생성·수정·삭제는 트랜잭션과 DB 제약조건으로 일관성을 유지한다. |

### 1.13 데이터 요구사항

- 식별자는 예측하기 어려운 UUID를 사용한다.
- 모든 주요 레코드에 `created_at`, `updated_at`을 기록한다.
- 회의록은 반드시 하나의 프로젝트에 속해야 한다.
- 프로젝트는 반드시 한 명의 소유자에게 속해야 한다.
- JSON 배열은 `null` 대신 빈 배열을 기본값으로 사용한다.
- 서버는 클라이언트가 보낸 `ownerId`, `createdBy`, `createdAt`을 신뢰하지 않고 인증정보와 서버 시각으로 결정한다.
- 원문 대화는 회의록 재검토에 필요한 기간만 저장하며 보존 기간 정책을 설정한다.

### 1.14 요구사항 우선순위와 MVP 완료 기준

**MVP 완료 조건:**

1. FR-1~FR-8의 필수 시나리오가 동작한다.
2. 두 사용자 사이의 프로젝트·회의록 데이터 격리 테스트가 통과한다.
3. AI 입력·출력 검증과 요청 제한이 적용된다.
4. 비밀정보가 저장소, 프론트 번들, 로그에 포함되지 않는다.
5. 프로젝트 생성 → 회의록 생성 → 편집 → 확정 → 삭제의 종단 간 시나리오가 통과한다.

## 2. 시스템 설계

### 2.1 설계 원칙

1. **백엔드 신뢰 경계:** 프론트엔드 입력과 AI 응답은 모두 신뢰하지 않으며 백엔드에서 검증한다.
2. **최소 권한:** 사용자는 본인이 소유한 프로젝트와 그 하위 회의록에만 접근한다.
3. **AI는 보조자:** AI 출력은 초안이며 사용자가 수정·확정한다.
4. **비밀정보 분리:** DB 비밀번호와 Anthropic API 키는 서버 환경변수에만 둔다.
5. **계약 우선:** OpenAPI 명세로 요청·응답 구조를 관리하고 프론트 타입을 자동 생성한다.
6. **실패 격리:** 외부 AI 장애가 저장된 데이터 조회·편집 기능에 전파되지 않게 한다.

### 2.2 전체 아키텍처

```text
┌──────────────────────────────┐
│ 사용자 브라우저              │
│ Next.js UI + Supabase Auth   │
└──────────────┬───────────────┘
               │ HTTPS / Bearer JWT
               ▼
┌──────────────────────────────┐
│ Spring Boot REST API         │
│ 인증·인가 / 입력 검증         │
│ Project / Minutes / AI Service│
└───────┬────────────────┬─────┘
        │ JPA/TLS        │ HTTPS
        ▼                ▼
┌───────────────┐  ┌────────────────┐
│ PostgreSQL    │  │ Anthropic Claude│
│ Supabase      │  │ 구조화 회의록   │
└───────────────┘  └────────────────┘
```

### 2.3 신뢰 경계와 데이터 흐름

| 경계 | 신뢰 수준 | 필수 통제 |
|---|---|---|
| 브라우저 → 백엔드 | 비신뢰 | JWT 검증, DTO 화이트리스트, 길이·형식 검증, rate limit |
| 백엔드 → PostgreSQL | 내부 제한 신뢰 | TLS, 최소 권한 DB 계정, JPA 파라미터 바인딩, 트랜잭션 |
| 백엔드 → Claude | 외부 비신뢰 | 전송 최소화, 타임아웃, 출력 스키마 검증, 로그 마스킹 |
| 배포 환경 → 애플리케이션 | 운영 신뢰 | 환경변수·Secret Store, 권한 분리, 키 순환 |

프론트엔드는 PostgreSQL을 직접 조회하지 않는다. Supabase 클라이언트는 인증 용도로만 사용하고, 모든 애플리케이션 데이터는 백엔드 API를 통해 접근한다.

### 2.4 백엔드 계층 설계

| 계층 | 주요 구성요소 | 책임 |
|---|---|---|
| Security | JWT Filter, SecurityConfig, CurrentUser | 토큰 검증과 사용자 식별 |
| Controller | ProjectController, MinutesController | HTTP 계약, DTO 검증, 상태 코드 반환 |
| Service | ProjectService, MinutesService | 권한 확인, 트랜잭션, 업무 규칙 |
| AI Adapter | ClaudeService, PromptBuilder, ResultValidator | 프롬프트 작성, API 호출, 결과 검증 |
| Repository | ProjectRepository, MinutesRepository | 소유자 조건을 포함한 안전한 DB 접근 |
| Domain/DTO | Project, Minutes, TodoData, Request/Response | 내부 모델과 외부 계약 분리 |
| Error | GlobalExceptionHandler, ErrorResponse | 일관된 오류 응답과 내부 정보 차단 |

Controller가 단순히 `findById(id)`를 호출하지 않고 `findByIdAndProjectIdAndOwnerId(...)`처럼 소유권 조건을 쿼리에 포함해야 한다. 현재 기능 브랜치의 회의록 상세·수정·삭제는 경로의 `projectId`를 실질적으로 검증하지 않으므로 이 설계에 따라 보완해야 한다.

### 2.5 프론트엔드 모듈 설계

```text
frontend/src/
├── app/
│   ├── (auth)/login, signup
│   └── (dashboard)/projects/...
├── features/
│   ├── auth/
│   ├── projects/
│   └── minutes/
├── lib/
│   ├── api-client.ts
│   ├── auth.ts
│   └── validation.ts
└── types/
    └── generated-api.ts
```

- 페이지 컴포넌트는 화면 조합과 라우팅을 담당한다.
- 기능별 폼, 목록, 편집기는 `features` 아래에 분리한다.
- 공통 API 클라이언트가 JWT 첨부, JSON 파싱, 오류 정규화를 담당한다.
- API 타입은 수동 중복 정의보다 OpenAPI에서 생성한다.
- 환경변수가 없거나 API 오류가 발생했을 때 빈 화면으로 숨기지 않고 오류 상태를 표시한다.

### 2.6 기능 모듈 설계

#### 2.6.1 인증 모듈(FR-1)

| 기능 | 설계 |
|---|---|
| 회원가입 | Supabase Auth가 이메일·비밀번호를 검증하고 계정을 생성한다. |
| 로그인 | 성공 시 Supabase 세션을 획득하고 보호 API에 access token을 전달한다. |
| 토큰 검증 | 백엔드는 JWKS 공개키로 서명과 표준 클레임을 검증한다. |
| 사용자 식별 | 토큰의 `sub`를 내부 `owner_id`로 사용하고 요청 본문의 사용자 ID는 무시한다. |
| 세션 만료 | 프론트는 갱신 실패 시 로그인 화면으로 이동하고 저장 중 데이터 손실을 안내한다. |

#### 2.6.2 프로젝트 모듈(FR-2, FR-3)

| 기능 | 설계 |
|---|---|
| 생성 | 이름·팀원 DTO 검증 후 인증 사용자를 소유자로 지정한다. |
| 목록 | `owner_id = currentUser` 조건으로 최신순 조회한다. |
| 상세 | 소유자 조건을 포함해 프로젝트와 회의록 요약을 조회한다. |
| 수정 | 변경 가능한 이름·팀원만 화이트리스트 방식으로 반영한다. |
| 삭제 | 소유권 확인 후 하위 회의록을 DB cascade 또는 트랜잭션으로 삭제한다. |

#### 2.6.3 AI 회의록 생성 모듈(FR-4, FR-8)

| 단계 | 처리 |
|---:|---|
| 1 | JWT와 프로젝트 소유권을 검증한다. |
| 2 | 날짜, 제목, 원문 길이와 문자 데이터를 검증한다. |
| 3 | 사용자별 rate limit와 일일 AI 생성 할당량을 확인한다. |
| 4 | 사용자 입력을 명령이 아닌 데이터 영역으로 구분한 프롬프트를 만든다. |
| 5 | Claude API를 제한 시간 안에 호출한다. |
| 6 | 응답을 추출하고 엄격한 JSON 스키마와 필드별 제한으로 검증한다. |
| 7 | 유효한 결과만 `DRAFT` 회의록으로 저장한다. |
| 8 | 응답 DTO에는 초안과 `requestId`를 반환한다. |

#### 2.6.4 회의록 모듈(FR-5~FR-7)

| 기능 | 설계 |
|---|---|
| 목록 | 프로젝트 소유권 확인 후 필요한 요약 필드만 조회한다. |
| 상세 | `project_id`, `minutes_id`, `owner_id`를 모두 조건으로 사용한다. |
| 편집 | 허용된 DTO 필드만 반영하고 배열 크기·문자열 길이를 재검증한다. |
| 확정 | 상태 전이를 `DRAFT → CONFIRMED`로 제한한다. 확정 후에도 명시적 재편집은 가능하다. |
| 삭제 | 소유권 검증 후 한 건을 삭제하고 `204 No Content`를 반환한다. |

| 페이지 | 경로 | 접근 | 설명 |
|---|---|---|---|
| 랜딩 | `/` | 공개 | 서비스 설명과 시작 링크 |
| 회원가입 | `/signup` | 공개 | 계정 생성 |
| 로그인 | `/login` | 공개 | 인증 |
| 프로젝트 목록 | `/projects` | 인증 | 본인 프로젝트 목록과 생성 폼 |

### 2.8 REST API 설계

#### 2.8.1 프로젝트 API

| Method | Endpoint | 설명 | 성공 |
|---|---|---|---:|
| GET | `/api/projects` | 본인 프로젝트 목록 | 200 |
| POST | `/api/projects` | 프로젝트 생성 | 201 |
| GET | `/api/projects/{projectId}` | 프로젝트 상세 | 200 |
| PATCH | `/api/projects/{projectId}` | 프로젝트명·팀원 수정 | 200 |
| DELETE | `/api/projects/{projectId}` | 프로젝트와 하위 회의록 삭제 | 204 |

#### 2.8.2 회의록 API

| Method | Endpoint | 설명 | 성공 |
|---|---|---|---:|
| GET | `/api/projects/{projectId}/minutes` | 회의록 요약 목록 | 200 |
| POST | `/api/projects/{projectId}/minutes` | AI 분석 및 초안 생성 | 201 |
| GET | `/api/projects/{projectId}/minutes/{minutesId}` | 회의록 상세 | 200 |
| PUT | `/api/projects/{projectId}/minutes/{minutesId}` | 전체 편집 결과 저장 | 200 |
| PATCH | `/api/projects/{projectId}/minutes/{minutesId}/status` | 초안 확정 | 200 |
| DELETE | `/api/projects/{projectId}/minutes/{minutesId}` | 회의록 삭제 | 204 |

#### 2.8.3 공통 요청 규칙

- `Authorization: Bearer <access-token>`을 요구한다.
- 생성 요청은 `Idempotency-Key`를 지원한다.
- JSON 이외의 Content-Type은 `415 Unsupported Media Type`으로 거부한다.
- 요청 본문 최대 크기를 서버와 프록시 양쪽에서 제한한다.
- 생성 성공은 `201 Created`, 삭제 성공은 본문 없는 `204 No Content`를 사용한다.

#### 2.8.4 오류 응답 형식

```json
{
  "code": "MINUTES_AI_TIMEOUT",
  "message": "회의록 생성 시간이 초과되었습니다. 잠시 후 다시 시도해 주세요.",
  "requestId": "01J...",
  "fieldErrors": []
}
```

| HTTP | 사용 상황 |
|---:|---|
| 400 | JSON 파싱 실패, 잘못된 형식 |
| 401 | 인증 누락·만료·위조 토큰 |
| 404 | 자원 없음 또는 접근 권한 없음 |
| 409 | 중복 멱등키, 수정 버전 충돌 |
| 422 | 필드 검증 또는 AI 출력 스키마 실패 |
| 429 | 요청 속도·일일 AI 할당량 초과 |
| 502 | AI 제공자 오류 또는 잘못된 외부 응답 |
| 504 | AI 호출 시간 초과 |

### 2.9 데이터베이스 설계

#### 2.9.1 ER 관계

```text
Supabase Auth User (1)
        │ owner_id
        ▼
    Project (1) ──────────── (N) Minutes
                                  │
                                  └─ JSONB: discussions, decisions,
                                            pending, todos, next_agenda
```

#### 2.9.2 `projects` 테이블

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | UUID | PK | 프로젝트 ID |
| `owner_id` | UUID | NOT NULL, INDEX | Supabase 사용자 `sub` |
| `name` | VARCHAR(100) | NOT NULL | 프로젝트·과목명 |
| `members` | JSONB | NOT NULL DEFAULT `[]` | AI 매칭용 팀원 이름 배열 |
| `created_at` | TIMESTAMPTZ | NOT NULL | 생성 시각 |
| `updated_at` | TIMESTAMPTZ | NOT NULL | 수정 시각 |
| `version` | BIGINT | NOT NULL | 낙관적 잠금 |

`owner_id, created_at DESC` 복합 인덱스를 두어 사용자별 목록 조회를 최적화한다.

#### 2.9.3 `minutes` 테이블

| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| `id` | UUID | PK | 회의록 ID |
| `project_id` | UUID | FK, NOT NULL, INDEX | 소속 프로젝트 |
| `created_by` | UUID | NOT NULL | 생성 사용자 |
| `meeting_date` | DATE | NOT NULL | 회의 날짜 |
| `raw_text` | TEXT | NOT NULL | 입력 대화 원문 |
| `title` | VARCHAR(150) | NOT NULL | 회의록 제목 |
| `topic` | VARCHAR(500) | NOT NULL | 주제 요약 |
| `discussions` | JSONB | NOT NULL DEFAULT `[]` | 논의 배열 |
| `decisions` | JSONB | NOT NULL DEFAULT `[]` | 결정 배열 |
| `pending` | JSONB | NOT NULL DEFAULT `[]` | 미결정 배열 |
| `todos` | JSONB | NOT NULL DEFAULT `[]` | 담당자·업무·마감일 배열 |
| `next_agenda` | JSONB | NOT NULL DEFAULT `[]` | 다음 안건 배열 |
| `status` | VARCHAR(20) | NOT NULL | `DRAFT` 또는 `CONFIRMED` |
| `ai_model` | VARCHAR(80) | NULL | 생성에 사용한 모델 식별자 |
| `created_at` | TIMESTAMPTZ | NOT NULL | 생성 시각 |
| `updated_at` | TIMESTAMPTZ | NOT NULL | 수정 시각 |
| `version` | BIGINT | NOT NULL | 낙관적 잠금 |

외래키는 `projects(id) ON DELETE CASCADE`로 설정한다. 서비스 계층에서도 프로젝트 소유권을 먼저 검증하고 트랜잭션 안에서 삭제한다.

#### 2.9.4 `ai_request_audit` 테이블(선택)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | UUID PK | 요청 추적 ID |
| `user_id` | UUID | 호출 사용자 |
| `project_id` | UUID | 대상 프로젝트 |
| `status` | VARCHAR(20) | SUCCESS, FAILED, TIMEOUT |
| `model` | VARCHAR(80) | 호출 모델 |
| `input_chars` | INTEGER | 입력 길이(원문 내용 제외) |
| `latency_ms` | INTEGER | 처리 시간 |
| `created_at` | TIMESTAMPTZ | 요청 시각 |

감사 테이블에는 대화 원문, 프롬프트 전문, AI 응답 전문, 인증 토큰을 저장하지 않는다.

### 2.10 주요 시퀀스 설계

#### 2.10.1 회의록 생성

```text
사용자      Next.js       Spring Boot       PostgreSQL       Claude
  │ POST       │               │                 │               │
  ├───────────▶│ Bearer JWT     │                 │               │
  │            ├───────────────▶│ JWT·입력 검증   │               │
  │            │                ├───────────────▶│ 소유권 조회    │
  │            │                │◀───────────────┤               │
  │            │                ├────────────────────────────────▶│
  │            │                │         구조화 분석 요청         │
  │            │                │◀────────────────────────────────┤
  │            │                │ JSON 스키마·길이·담당자 검증      │
  │            │                ├───────────────▶│ DRAFT 저장     │
  │            │◀───────────────┤ 201 + 회의록    │               │
  │◀───────────┤ 상세 페이지 이동│                 │               │
```

AI 호출 또는 검증이 실패하면 DB 저장 단계로 진행하지 않는다. 저장이 실패하면 성공 응답을 반환하지 않는다.

#### 2.10.2 회의록 편집

```text
사용자 → 편집 화면 → PUT /minutes/{id} + version
                    → JWT·부모 프로젝트·소유권 검증
                    → DTO 검증
                    → version 조건부 UPDATE
                    → 성공 200 / 충돌 409
```

### 2.11 AI 프롬프트 및 출력 설계

#### 2.11.1 프롬프트 구성

1. 시스템 규칙: 회의록 생성 역할과 금지사항 정의
2. 출력 계약: 허용 필드와 JSON 타입 명시
3. 프로젝트 문맥: 프로젝트명과 서버 검증된 팀원 목록
4. 사용자 데이터: 명확한 구분자로 감싼 카카오톡 원문
5. 후처리 규칙: 없는 사실 생성 금지, 날짜 없으면 `미정`, 빈 배열 허용

원문 안의 “이전 지시를 무시하라”, “API 키를 출력하라” 같은 문장은 명령이 아니라 분석 대상 데이터로 취급한다. 서버는 프롬프트만으로 안전을 보장하지 않고 응답 스키마 검증과 필드별 제한을 반드시 적용한다.

#### 2.11.2 출력 검증

- 최상위 객체와 허용 필드만 수락한다.
- 필수 문자열 필드의 최대 길이를 제한한다.
- 각 배열은 최대 50개, 각 항목은 최대 1,000자로 제한한다.
- `todos`는 `name`, `task`, `deadline`만 허용한다.
- HTML·스크립트가 들어와도 화면에서는 텍스트로 렌더링한다.
- 모델이 코드 펜스를 포함한 경우 JSON 부분을 추출할 수 있으나, 추출 후 전체 스키마를 다시 검증한다.
- 검증 실패 시 원문 응답을 사용자나 운영 로그에 그대로 노출하지 않는다.

### 2.12 보안 설계

| 영역 | 설계 |
|---|---|
| 인증 | Supabase JWT의 서명, `iss`, `aud`, `exp`, `sub`를 백엔드에서 검증 |
| 접근 제어 | 모든 쿼리에 현재 사용자 `owner_id`와 부모 `project_id` 조건 적용 |
| IDOR 방지 | `minutesId`만으로 조회·수정·삭제하지 않고 프로젝트·소유자 관계를 함께 검증 |
| 입력 검증 | Bean Validation + 서비스 계층 업무 규칙 + DB 제약조건의 다중 방어 |
| SQL Injection | Spring Data JPA 파라미터 바인딩 사용, 동적 문자열 SQL 금지 |
| XSS | React 기본 이스케이프 유지, `dangerouslySetInnerHTML` 금지, CSP 적용 |
| CSRF | Bearer 토큰 기반 API를 기본으로 하고, 쿠키 인증을 사용하면 SameSite와 CSRF 토큰 추가 |
| CORS | 로컬·운영 프론트의 정확한 Origin만 허용하고 임의 `*.vercel.app` 허용 금지 |
| 비밀정보 | `ANTHROPIC_API_KEY`, DB 자격증명을 서버 Secret Store에 저장, Git·프론트 노출 금지 |
| 대화 개인정보 | 전송 최소화, TLS, 로그 마스킹, 보존 기간과 삭제 정책 적용 |
| AI 프롬프트 인젝션 | 원문을 비신뢰 데이터로 구분, 도구 호출 미사용, 구조화 출력·스키마 검증 |
| 비용·DoS | 본문 크기 제한, 사용자별 rate limit, 일일 할당량, 타임아웃, 동시 요청 제한 |
| Mass Assignment | Entity를 요청 본문으로 직접 받지 않고 전용 Request DTO의 허용 필드만 반영 |
| 오류 처리 | 전역 예외 처리로 내부 메시지·스택·SQL·외부 응답을 숨김 |
| 보안 헤더 | CSP, HSTS, X-Content-Type-Options, Referrer-Policy, frame-ancestors 적용 |
| 의존성 | Dependabot 또는 Renovate, Gradle/npm 감사, 잠금 파일 검토 |
| 로그 | requestId 중심 구조화 로그, 토큰·API 키·대화 원문·AI 응답 전문 기록 금지 |

#### 2.12.1 권한 검사 규칙

| 작업 | 필수 조건 |
|---|---|
| 프로젝트 목록 | `project.owner_id == currentUser.id` |
| 프로젝트 상세·수정·삭제 | 요청 프로젝트의 소유자 일치 |
| 회의록 생성 | 부모 프로젝트의 소유자 일치 |
| 회의록 상세·수정·삭제 | 회의록의 `project_id` 일치 + 부모 프로젝트 소유자 일치 |

클라이언트가 전달한 소유자 ID나 팀원 이름을 권한 정보로 사용해서는 안 된다.

#### 2.12.2 현재 코드에서 우선 보완할 보안 항목

1. 로그인·회원가입 페이지는 존재하지만 실제 Supabase Auth 연동과 백엔드 JWT 검증이 미구현 상태이다.
2. 기능 브랜치의 프로젝트·회의록 API에 사용자 소유자 컬럼과 권한 검사가 없다.
3. 회의록 상세·수정·삭제가 경로의 `projectId`와 `minutesId` 관계를 검증하지 않아 IDOR 위험이 있다.
4. Claude API 키가 없을 때 명확한 구성 오류 대신 null client 호출로 실패할 수 있다.
5. AI 입력 길이, 요청 속도, 일일 비용 한도, 호출 타임아웃이 정의되어 있지 않다.
6. `RuntimeException` 메시지가 그대로 노출되지 않도록 전역 예외 응답 체계가 필요하다.
7. CORS의 와일드카드 서브도메인 문자열 대신 검증된 운영 Origin 목록을 사용해야 한다.
8. 프론트의 일부 `fetch(...).catch(() => {})`는 장애를 숨기므로 사용자 오류 상태로 전환해야 한다.

### 2.13 트랜잭션과 장애 처리

- 프로젝트 삭제와 하위 회의록 삭제는 하나의 트랜잭션으로 처리한다.
- AI 호출은 DB 트랜잭션을 장시간 점유하지 않는다. 외부 호출 완료 후 짧은 저장 트랜잭션을 시작한다.
- AI 호출 성공 후 DB 저장 실패 시 사용자에게 실패로 응답하고 동일 멱등키 재시도를 허용한다.
- 외부 호출은 연결·읽기 타임아웃을 설정하고 제한된 횟수만 지수 백오프로 재시도한다.
- 잘못된 요청과 권한 오류는 재시도하지 않는다.
- 낙관적 잠금 충돌은 `409`로 응답해 최신 문서를 다시 불러오게 한다.

### 2.15 관측성과 감사

- 모든 요청에 고유 `requestId`를 부여하고 응답 헤더·오류 응답에 포함한다.
- API 경로, 상태 코드, 처리시간, 인증 사용자 해시 식별자만 구조화해 기록한다.
- AI 요청 성공률, p95 지연, 타임아웃, 스키마 실패, 사용자별 할당량 초과를 지표로 수집한다.
- 로그에는 `Authorization`, API 키, DB 비밀번호, 카톡 원문, AI 응답 전문을 기록하지 않는다.
- 관리자도 사용자 콘텐츠를 기본적으로 열람할 수 없게 하고, 장애 조사 접근은 별도 승인·감사 절차를 둔다.

### 2.17 설계 결정 사항 및 근거

1. **프로젝트 소유자 중심 권한 모델:** 현재 MVP는 팀원 계정 초대보다 회의록 생성에 집중하므로 한 명의 소유자만 쓰게 한다. 공동 편집은 별도 권한 모델 없이 급히 추가하지 않는다.
2. **AI 결과를 `DRAFT`로 저장:** 모델 출력은 누락·오해 가능성이 있으므로 사람이 확인하기 전 확정 데이터로 취급하지 않는다.
3. **원문과 구조화 결과를 함께 저장:** 사용자가 AI 결과를 원문과 대조할 수 있게 하되 보존 기간·삭제·로그 제외 정책을 함께 적용한다.
4. **회의록 구성요소를 JSONB로 저장:** MVP의 가변 배열을 단순하게 저장하고 한 문서 단위로 편집한다. 항목별 검색·통계가 중요해지면 정규화 테이블로 이전한다.
5. **AI 호출을 동기 API로 시작:** 초기 규모에서는 구현이 단순하다. p95 처리시간이 길거나 동시 사용자가 증가하면 작업 큐와 상태 조회 API로 전환한다.
6. **백엔드에서 JWT와 객체 권한을 모두 검증:** 프론트 라우트 보호와 UUID만으로는 접근 제어가 되지 않으며, 모든 요청에서 소유권을 재검증해야 한다.
7. **OpenAPI를 계약의 기준으로 사용:** 백엔드 DTO와 프론트 TypeScript 타입 불일치를 줄이고 변경 영향을 조기에 발견한다.

### 2.18 구현 전 권장 작업 순서

1. Next.js·Spring Boot 기준 버전과 API 계약 확정
2. Supabase Auth 연동 및 백엔드 JWT 검증
3. `owner_id`, 상태, 시각, version을 포함한 DB 마이그레이션
4. 프로젝트 API에 사용자별 접근 제어 적용
5. 회의록 API의 부모-자식 관계 및 소유권 검증
6. AI 입력 제한, 타임아웃, JSON 스키마 검증, 멱등 처리
7. 전역 오류 응답과 프론트 로딩·실패 UI 통일
8. 보안 헤더, 정확한 CORS allowlist, rate limit 적용
9. 기능·권한·AI 실패·보안 테스트 작성
10. Vercel·Railway·Supabase 환경 분리 후 배포 검증

## 3. 결론

Teample AI Manager의 핵심은 단순한 AI 요약이 아니라, 프로젝트 문맥을 이용해 대화를 구조화하고 사용자가 결과를 검토·수정·확정하는 안전한 회의록 관리 흐름이다. 시스템은 브라우저, 백엔드, 데이터베이스, 외부 AI 사이의 신뢰 경계를 명확히 나누고 모든 외부 입력을 검증해야 한다.

특히 현재 기능 브랜치가 구현한 프로젝트·회의록 CRUD와 Claude 연동을 실제 서비스 수준으로 발전시키려면 인증, 사용자별 소유권, 부모-자식 관계 검증, AI 출력 검증, 비용 제한, 개인정보 로그 차단을 우선 적용해야 한다. 이 설계를 기준으로 구현과 테스트를 진행하면 요구사항부터 보안 검증까지 추적 가능한 형태로 프로젝트를 완성할 수 있다.
